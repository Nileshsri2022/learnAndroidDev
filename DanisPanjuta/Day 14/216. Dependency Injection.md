# Dependency Injection

---

## Overview

*Dependency Injection (DI)* is passing a class its dependencies rather than having it construct them. This lecture contrasts **manual DI** (what the Wishlist uses via `Graph`) with **framework DI** (Hilt/Dagger) and motivates why `WishViewModel` takes `WishRepository` as a constructor parameter instead of creating it.

---

## Manual vs framework

| Approach | How dependencies are provided | Example |
| :--- | :--- | :--- |
| **Manual DI (Graph)** | A singleton `object Graph` holds instances and hands them out | `WishViewModel(wishRepository = Graph.wishRepository)` |
| **Constructor injection** | Caller passes the dependency as a param | `WishViewModel(repo)` — test can pass a fake `repo` |
| **Hilt/Dagger** | Framework generates the graph, injects fields/constructors | `@Inject WishRepository` — larger apps, more setup |

The Wishlist uses **manual DI via `Graph`** — lightweight, no extra library beyond Room.

---

## Why inject `WishRepository`?

```kotlin
class WishViewModel(private val wishRepository: WishRepository = Graph.wishRepository): ViewModel()
```

| Benefit | Explanation |
| :--- | :--- |
| **Testability** | In a unit test: `WishViewModel(FakeWishRepository())` without touching Room |
| **Flexibility** | Swap `WishRepository` for `NetworkWishRepository` without changing the ViewModel |
| **Single source** | One `WishDatabase` + one `WishRepository` for the whole process — not rebuilt per screen |

Defaulting to `Graph.wishRepository` keeps call sites `WishViewModel()` simple while still allowing tests to override.

---

## Recap / cheat sheet

- **DI:** class receives dependencies rather than newing them.
- **Wishlist DI:** `Graph` singleton + constructor param with default `Graph.wishRepository`.
- **Test:** pass a fake `WishRepository` to `WishViewModel(fake)` — no DB needed.
