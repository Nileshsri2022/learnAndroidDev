# Why MVVM, and Why a Repository

---

## Overview

This lecture is the "why". MVVM and repositories feel like a lot of abstraction and boilerplate, and
that abstraction is exactly the point. Here are the concrete reasons.

---

## Part 1 — Why MVVM

### 1. Separation of concerns

MVVM promotes a clear separation between the **user interface**, the **business logic** and the
**data**. Each component has a distinct responsibility, which makes the codebase organised and
easier to maintain.

### 2. Testability

Because of that separation, you can test each component **independently**. You can test the
ViewModel without involving the user interface or the data source.

### 3. Reusability

ViewModels are decoupled from the view, so the same ViewModel can be reused across different views —
or even across different platforms in a multi-platform app.

### 4. Data binding

MVVM can be paired with data binding mechanisms, allowing automatic updates between the ViewModel
and the view. This reduces boilerplate and keeps the UI always in sync with the data.

### 5. Maintainability

As the app grows, distinct layers help you manage the complexity. **Changing the user interface
won't affect the underlying business logic, and vice versa.**

---

### The one-sentence version

> MVVM buys you the ability to change one layer without touching the other two.

| Benefit | What it saves you from |
| :--- | :--- |
| Separation of concerns | God classes |
| Testability | Needing a device/emulator to test logic |
| Reusability | Rewriting the same logic per screen |
| Data binding | Manual sync code |
| Maintainability | Rewriting the app after a redesign |

---

## Part 2 — Why a Repository

> A repository is a design pattern that acts as a clean API for data access to the rest of the
> application. Think of it as a mediator between different data sources such as remote APIs, local
> databases, and in-memory caches.

### 1. Abstraction

It provides a higher-level abstraction over raw data sources, so you can **switch data sources
without changing the rest of the application**.

> Today you get the data from the web. Tomorrow you don't get it from the web anymore, you get it
> from a database. Cool — no problem. Just plug and play.

### 2. Centralised data handling

All data-related operations are centralised in the repository, ensuring consistency and reducing
redundancy.

### 3. Isolation

By isolating data-related code, you can easily **mock data for testing**, change the storage
mechanism, or add caching layers **without affecting the rest of the app**.

### 4. Flexibility

If you later change how you fetch or store data — moving from one database solution to another, or
adding a cloud backup — you only update the repository. The ViewModel and the view stay untouched.

---

## The analogy — chef and supplier

You are a **chef** in a restaurant. You are the **view**.

The ingredients you need can come from many places:

* a **farm**
* a **local market**
* your **own garden**

These are the **different data sources**.

Instead of going to each of them every time you cook, you have a **trusted supplier** — the
**repository** — who fetches the best ingredients for you. The supplier knows where to get each
ingredient, when to harvest it, and how to store it.

You, the chef, only care about **receiving the right ingredients for your dish**. The supplier
abstracts away the complexity of sourcing.

| Restaurant | MVVM |
| :--- | :--- |
| The chef | The **view** |
| The dish (what the customer ordered) | The **UI state** |
| Farm / market / garden | Remote API / database / cache |
| The trusted supplier | The **repository** |
| Knowing when to harvest and how to store | Caching, sync, error handling |

---

## Verdict

MVVM and repositories **might seem complex initially**, but they offer long-term benefits —
especially for larger applications. Their structured approach aids in:

* managing complexity
* ensuring scalability
* improving maintainability

> you to understand *why* we're doing it — because we need to set it up so that it will be available
> inside the main activity, so that we can actually run our application again."
