## Theme

**MVVM architecture** — moving state and logic out of the UI into a `ViewModel`, with a Model and a
Repository underneath — plus the Kotlin OOP keywords that make it possible.

---

## The architecture in one picture

```
   MainActivity                    ── VIEW ──
   (composables)
        │  reads state
        │  fires events (onClick)
        ▼
   CounterViewModel : ViewModel()  ── VIEWMODEL ──
        │  holds Compose state
        │  calls the repository
        ▼
   CounterRepository               ── REPOSITORY ──
        │  private data + clean API
        ▼
   CounterModel(count: Int)        ── MODEL ──
```

## The final code

**`CounterModel.kt`**

```kotlin
data class CounterModel(
    val count: Int
)

class CounterRepository {

    private var counter = CounterModel(count = 0)

    fun getCounter(): CounterModel = counter

    fun incrementCounter() {
        counter = counter.copy(count = counter.count + 1)
    }

    fun decrementCounter() {
        counter = counter.copy(count = counter.count - 1)
    }
}
```

**`CounterViewModel.kt`**

```kotlin
class CounterViewModel : ViewModel() {

    private val _repository = CounterRepository()

    private val _count = mutableStateOf(_repository.getCounter().count)
    val count: MutableState<Int> = _count

    fun increment() {
        _repository.incrementCounter()
        _count.value = _repository.getCounter().count
    }

    fun decrement() {
        _repository.decrementCounter()
        _count.value = _repository.getCounter().count
    }
}
```

**`MainActivity.kt`**

```kotlin
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {

            val viewModel: CounterViewModel = viewModel()

            Surface(
                modifier = Modifier.fillMaxSize(),
                color = MaterialTheme.colorScheme.background
            ) {
                CounterApp(viewModel)
            }
        }
    }
}
```

**The composable**

```kotlin
@Composable
fun CounterApp(viewModel: CounterViewModel) {
    Column(
        modifier = Modifier.fillMaxSize(),
        verticalArrangement = Arrangement.Center,
        horizontalAlignment = Alignment.CenterHorizontally
    ) {
        Text("${viewModel.count.value}", fontSize = 24.sp, fontWeight = FontWeight.Bold)
        Spacer(modifier = Modifier.height(16.dp))
        Row {
            Button(onClick = { viewModel.increment() }) { Text("Increment") }
            Button(onClick = { viewModel.decrement() }) { Text("Decrement") }
        }
    }
}
```

## Kotlin OOP cheat sheet

| Keyword | Meaning | Example |
| :--- | :--- | :--- |
| `open class X` | X can be inherited from | `open class BaseClass` |
| `class Y : X()` | Y inherits everything X has | `class Secondary : BaseClass()` |
| `open fun f()` | f can be overridden | `open fun role()` |
| `override fun f()` | replace the inherited f | `override fun role()` |
| `super.f()` | run the parent's f | `super.role()` |
| `interface I` | a contract of capabilities | `interface Singer` |
| `class Y : X(), I, J` | one parent, many interfaces | `class Offspring : Secondary(), Archer, Singer` |
| `private val _x` | private backing property | `private val _count` |
| `val x = _x` | public read-only window | `val count: MutableState<Int> = _count` |

### Inheritance vs interface

| | Class inheritance | Interfaces |
| :--- | :--- | :--- |
| How many | one parent | any number |
| Needs `open` | yes | no (implicitly overridable) |
| Brings | state + behaviour | behaviour only |
| Used for | "is-a" | "can-do" |

## Why MVVM (5 reasons)

1. **Separation of concerns** — UI, logic and data each get a distinct responsibility
2. **Testability** — test the ViewModel without the UI or the data source
3. **Reusability** — ViewModels are decoupled from the view
4. **Data binding** — automatic updates between ViewModel and view
5. **Maintainability** — changing the UI doesn't touch the business logic

## Why a Repository (4 reasons)

1. **Abstraction** — swap web / database / cache without touching the rest of the app
2. **Centralised data handling** — consistency, less redundancy
3. **Isolation** — easy to mock data for testing, change storage, add caching
4. **Flexibility** — only the repository changes when the data source changes

## The bug that started it all

Rotating the phone is a **configuration change** → the Activity is destroyed and recreated →
`remember`-ed state is lost. `rememberSaveable` is a workaround; a `ViewModel` is the fix.
