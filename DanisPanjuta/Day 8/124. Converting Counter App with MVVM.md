# Converting the Counter App to MVVM

---

## Overview

Same app, restructured. The count and the two functions move out of `MainActivity` into a
`CounterViewModel` class, and the composable becomes a pure "dumb" UI that only reads state and
fires events.

---

## Step 1 — create the ViewModel

New → Kotlin File/Class → **`CounterViewModel`**.

The trick is making it "of a certain type":

```kotlin
class CounterViewModel : ViewModel() {
```

`ViewModel` is a class from AndroidX:

```kotlin
import androidx.lifecycle.ViewModel
```

It already defines how a ViewModel behaves, what methods it has and which properties exist. This is
**inheritance** — `MainActivity` does exactly the same thing with
`class MainActivity : ComponentActivity()`, which is where `override fun onCreate` and
`super.onCreate` come from. Those are "predefined pieces of code that say: this is what you have
to do if you want to use me".

---

## Step 2 — private state + a public read-only window

```kotlin
class CounterViewModel : ViewModel() {

    // private: only this class may touch it
    private val _count = mutableStateOf(0)

    // public: read-only from outside, still observable by Compose
    val count: MutableState<Int> = _count

    fun increment() {
        _count.value++
    }

    fun decrement() {
        _count.value--
    }
}
```

Two details from the lecture:

* **`private`** = the variable only exists / is accessible inside this class.
* **The leading underscore** is the naming convention for a private backing property. It lets you
  see at a glance: "this one is private".

Why expose it at all? Because the UI needs to know the current value. But it only gets the
**value**, not the variable itself — it cannot reassign `count` from outside because it is a `val`.
And because it is still a `MutableState`, Compose observes it and recomposes when `_count` changes.

> You do this so that you can add instructions later about *what happens* when somebody accesses
> it. Right now it looks arbitrary — but the pattern is what protects your internals.

---

## Step 3 — the composable receives the ViewModel

```kotlin
@Composable
fun CounterApp(viewModel: CounterViewModel) {

    Column(
        modifier = Modifier.fillMaxSize(),
        verticalArrangement = Arrangement.Center,
        horizontalAlignment = Alignment.CenterHorizontally
    ) {
        Text(
            text = "${viewModel.count.value}",
            fontSize = 24.sp,
            fontWeight = FontWeight.Bold
        )
        Spacer(modifier = Modifier.height(16.dp))
        Row {
            Button(onClick = { viewModel.increment() }) { Text("Increment") }
            Button(onClick = { viewModel.decrement() }) { Text("Decrement") }
        }
    }
}
```

Notice what disappeared: no `count` variable, no `increment()` / `decrement()` local functions.
The composable only *reads* (`viewModel.count.value`) and *asks* (`viewModel.increment()`).

---

## Step 4 — get the ViewModel in `MainActivity`

```kotlin
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {

            val viewModel: CounterViewModel = viewModel()

            UnitConverterTheme {   // or your app's theme
                Surface(
                    modifier = Modifier.fillMaxSize(),
                    color = MaterialTheme.colorScheme.background
                ) {
                    CounterApp(viewModel)
                }
            }
        }
    }
}
```

`viewModel()` needs the Compose lifecycle dependency — Android Studio offers it on hover:

```
androidx.lifecycle:lifecycle-viewmodel-compose
```

```kotlin
import androidx.lifecycle.viewmodel.compose.viewModel
```

`viewModel()` creates the instance **and keeps it alive** across configuration changes, so a
rotation re-runs `onCreate` but hands back the *same* ViewModel.

---

## Result

Increment to 5, rotate → the UI rebuilds, the state stays. The count is still 5.

---

## What we actually have so far

| Layer | Where it lives | Status |
| :--- | :--- | :--- |
| **M**odel | not yet | missing |
| **V**iew | `MainActivity` / composables | done |
| **V**iew**M**odel | `CounterViewModel` | done |

So right now it is really "VM", with the ViewModel double-duty as the data holder. The real Model
arrives in `Setting up the Model and the Repository for MVVM`.

---

## Takeaway

MVVM's most visible benefit here is **state that survives rotation**. But the bigger benefit — the
one that will show up in every later app — is that the UI stopped owning the logic.
