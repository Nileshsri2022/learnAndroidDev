# Setting Up the Model and the Repository for MVVM

---

## Overview

The ViewModel from the previous lecture still holds the data itself. Now the missing **M** arrives:
a `CounterModel` (the data) and a `CounterRepository` (the clean API to that data).

---

## Step 1 — the Model

New Kotlin class → **`CounterModel`**. It is a **data class**, and it is deliberately tiny:

```kotlin
data class CounterModel(
    val count: Int
)
```

One parameter, that's it. A model *could* be far more complex — all kinds of additional
information. Here it just contains a number.

> The course is honest about this: for a counter, a full MVVM setup is overkill. You saw how easy it
> was with the logic right inside the UI. The example exists so the pattern is understandable before
> you meet it in an app where it actually matters.

---

## Step 2 — the Repository

Created inside the same `CounterModel` file (a file can hold several declarations).

```kotlin
class CounterRepository {

    private var counter = CounterModel(count = 0)

    fun getCounter(): CounterModel {
        return counter
    }

    fun incrementCounter() {
        counter = counter.copy(count = counter.count + 1)
    }

    fun decrementCounter() {
        counter = counter.copy(count = counter.count - 1)
    }
}
```

### What each part does

| Member | Purpose |
| :--- | :--- |
| `private var counter` | The real data. Hidden behind `private` — nobody outside can touch it directly |
| `getCounter()` | The only read channel |
| `incrementCounter()` | The only way to add one |
| `decrementCounter()` | The only way to subtract one |

This is the same `private` + accessor pattern as `private val _count` / `val count` in the
ViewModel, applied one layer lower.

### A note on the mutation style

The lecture narrates `counter.count++` / `counter.count--`, which requires a `var` in the model.
Since `CounterModel` is a data class, the idiomatic Kotlin way is to **replace** it with `copy()`
(as written above). Same result — a new `CounterModel` with an updated count — and it keeps the
model immutable, which is what makes data classes safe to share.

---

## What a repository actually is

> A repository is a design pattern that acts as a **clean API** (Application Programming Interface)
> for data access to the rest of the application. Think of it as a **mediator** between different
> data sources such as remote APIs, local databases, and in-memory caches.

It is "plug and play". The data could come from:

* an API, somewhere in the cloud
* a database on the phone
* a simple in-memory variable or list

The repository is the converter that understands how the data comes in and turns it into what the
application can work with.

---

## Step 3 — the ViewModel now uses the repository

```kotlin
class CounterViewModel : ViewModel() {

    // Simplification for this part of the course — see the note below
    private val _repository = CounterRepository()

    private val _count = mutableStateOf(_repository.getCounter().count)
    val count: MutableState<Int> = _count

    fun increment() {
        _repository.incrementCounter()
        _count.value = _repository.getCounter().count
    }

    fun decrement() {
        _repository.decrementCounter()
        _count.value = _repository.getCounter().count
    }
}
```

### What changed

* **Before:** the ViewModel did `_count.value++` itself.
* **Now:** the ViewModel asks the repository to do it, then re-reads the value.

The **data logic** (how the count is stored and modified) lives entirely in the repository. The
ViewModel is only the manager between the view and the model.

---

## Why `_repository` is a property and not a constructor parameter

The proper way is:

```kotlin
class CounterViewModel(private val repository: CounterRepository) : ViewModel()
```

but that forces you to create a **ViewModel factory** and to get the repository from somewhere
external. To keep this section of the course simple, the repository is instantiated directly as a
`private val` inside the ViewModel.

> This line basically saves a lot of time that you would otherwise spend on a ViewModel factory and
> all that stuff.

Remember this: it is a shortcut for teaching, not the production pattern.

---

## Result

Run it. The app still works. Rotate it — the count is still 3.

Nothing in `MainActivity` changed at all. You refactored two classes underneath and the UI never
noticed.

---

## The stack, bottom to top

```
CounterModel          ← the data (data class)
      ▲
CounterRepository     ← the clean API to that data (private var + getters/mutators)
      ▲
CounterViewModel      ← the manager: holds Compose state, calls the repository
      ▲
MainActivity          ← the View: reads state, fires events
```
