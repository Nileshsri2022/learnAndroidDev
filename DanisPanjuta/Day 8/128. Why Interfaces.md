# Why Interfaces

---

## The story — the guilds of Crawfordsville

In the town of Crawfordsville there are many guilds, each representing a specific craft: the
blacksmiths' guild, the bakers' guild, the tailors' guild.

Each guild has a set of **standards and practices** — the *methods* its members must adhere to.

But some townsfolk are multi-talented. **Sir Bakelite** is not only a member of the bakers' guild,
but also follows the tailors' standards — making him both a **baker and a tailor**, i.e.
**implementing multiple interfaces**.

This multi-guild membership lets him offer a diverse range of services. And regardless of each
baker's personal style or technique, the guild guarantees certain quality standards — that is the
**contract** an interface enforces.

---

## Mapping the story

| Guilds of Crawfordsville | Kotlin |
| :--- | :--- |
| A guild | An `interface` |
| The guild's standards & practices | The functions the interface declares |
| A member | A `class` that implements the interface |
| Sir Bakelite, baker **and** tailor | `class X : A(), B()` |
| Quality guarantee | The compiler refuses to build if you don't implement |

## The five purposes of an interface

### 1. Abstraction

An interface defines a **contract** that classes can implement. The contract consists of method
signatures that derived classes **must** provide implementations for.

It abstracts the **what** from the **how**:

> A class can say "I promise to have this capability" without immediately specifying how it
> achieves it.

```kotlin
interface Singer {
    fun sing()   // WHAT — a promise
}               // no body saying HOW
```

### 2. Multiple inheritance

Most OO languages — Kotlin included — do **not** support multiple inheritance of classes, because
of the **diamond problem** and other complexities.

But a class can implement **multiple interfaces**, so you inherit from multiple sources without the
baggage of class-based multiple inheritance.

```kotlin
class Offspring : Secondary(), Archer, Singer   // one parent, many contracts
```

### 3. Flexibility and interchangeability

Since an interface focuses on the **what**, many different classes can implement the same interface
in completely different ways. That means objects of those classes can be used **interchangeably**
anywhere only the interface's capability is relevant.

```kotlin
val singer: Singer = Offspring()   // or any other Singer implementation
```

The calling code does not care *which* class it got.

### 4. Encapsulation

An interface hides the internal implementation of a class and exposes only the declared methods.
External components interact with the object through a well-defined contract — nothing else.

### 5. Evolution and scalability

As software grows, an interface provides a **stable contract**. You can expand and refactor the
underlying implementation without breaking the classes that depend on the interface.

```kotlin
// change everything inside Offspring — this line still compiles and works
val singer: Singer = Offspring()
```

---

## One-line summary

An interface is a **promise of capability**. It lets a class:

* commit to behaviour without exposing how it is done,
* learn from more than one source,
* be swapped for any other class making the same promise,
* stay replaceable while its internals change underneath.
