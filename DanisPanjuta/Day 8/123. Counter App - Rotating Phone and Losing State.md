# Counter App — Rotating the Phone and Losing State

---

## Overview

Before changing anything, the counter is built **the old-fashioned way**, exactly as in Day 5–7:
a `remember`-ed state inside the composable. Then a rotation exposes why that is not enough.

---

## Building it

New project → **Empty Activity** → name it `CounterMVVM`.

In `MainActivity.kt`, delete `Greeting` and `GreetingPreview`, then add the app:

```kotlin
@Composable
fun CounterApp() {
    val count = remember { mutableStateOf(0) }

    fun increment() {
        count.value++
    }

    fun decrement() {
        count.value--
    }

    Column(
        modifier = Modifier.fillMaxSize(),
        verticalArrangement = Arrangement.Center,
        horizontalAlignment = Alignment.CenterHorizontally
    ) {
        Text(
            text = "${count.value}",
            fontSize = 24.sp,
            fontWeight = FontWeight.Bold
        )
        Spacer(modifier = Modifier.height(16.dp))
        Row {
            Button(onClick = { increment() }) { Text("Increment") }
            Button(onClick = { decrement() }) { Text("Decrement") }
        }
    }
}
```

Imports needed: `Column`, `Row`, `Button`, `Spacer`, `remember`, `mutableStateOf`, `Arrangement`,
`Alignment`, `dp`, `sp`, `FontWeight`.

Run it — increment works, decrement works.

---

## The bug: rotate the phone

1. Increment to, say, 5.
2. Rotate the device to landscape.
3. The UI reloads… and the count is back to **0**.

### Why

Rotating the screen is a **configuration change**. Android destroys and recreates the Activity.
`remember` only survives **recomposition** — not Activity destruction. So every `remember`-ed
value is thrown away and re-initialised.

> Imagine the user is happily counting, rotates the phone, and their number is gone. That is a
> "such an insanely bad user experience".

---

## The workaround (and why it is not the answer)

```kotlin
val count = rememberSaveable { mutableStateOf(0) }
```

`rememberSaveable` survives configuration changes by writing the value into the `Bundle`. It works,
but:

* you need a **`Saver`** for anything that is not a primitive / simple type
* the state still lives inside the composable, so it dies with the screen it belongs to
* it does not scale once the data comes from a database or the network

Forcing a single orientation is also a workaround, not a fix.

---

## The actual fix

Store the state **outside** the composable, in a `ViewModel`. That is Day 8's whole point.

| | `remember` | `rememberSaveable` | `ViewModel` |
| :--- | :--- | :--- | :--- |
| Survives recomposition | yes | yes | yes |
| Survives rotation | no | yes | yes |
| Survives leaving the screen | no | no | yes |
| Lives outside the UI | no | no | yes |
