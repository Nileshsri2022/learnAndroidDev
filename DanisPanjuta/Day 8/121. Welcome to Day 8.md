# Welcome to Day 8

---

## Overview

Day 7 finished the first full Jetpack Compose app (the Shopping List). Today the topic is
**architecture** — specifically **MVVM** (Model – View – ViewModel) and the `ViewModel` class.

So far every app in this course has followed the same lazy pattern: put all the code inside
`MainActivity`, or move one composable into its own file. That is fine for a toy app and
terrible for a real one.

---

## Why architecture matters at all

| Approach | What it looks like | When it breaks |
| :--- | :--- | :--- |
| Everything in `MainActivity` | UI **and** logic in one class | Any app bigger than a demo |
| Composable in a separate file | Still no separation of logic vs. UI | As soon as data enters the picture |
| MVVM | UI / logic / data each get their own layer | Bigger team, longer lifetime |

The moment more than one person works on the app — one on the UI, one on how data gets into the
app — a single giant class becomes unmaintainable. Architecture is what keeps the roles apart.

---

## The app for today

A **counter**:

* increment a number
* decrement a number

Built **twice**:

1. **The old-fashioned way** — `remember { mutableStateOf(0) }` inside the composable.
2. **The MVVM way** — state and logic live in a `ViewModel`, the UI only reads and sends events.

Same behaviour, completely different structure.

---

## The reason you cannot ignore this

The course gives a very concrete reason: **a frozen user interface is not acceptable**.

If you load data from the internet on the main thread, the UI stops responding. The user sees a
frozen phone. Google will not approve that app, and users uninstall it.

So the UI layer must never own the heavy work. That is exactly what MVVM gives you — the UI asks,
the ViewModel decides, the Model/Repository fetches.

> "Once something is a little more complicated — especially once you're loading data from the
> internet and you're freezing your user interface — that would be an absolute no-go."
