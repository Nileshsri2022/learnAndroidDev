Here is a clear, structured breakdown of the lecture introducing **lists** — `listOf` and
`mutableListOf` — through the story of Joe's shopping trip.

---

### **1. The Story**

**Joe**, an Android developer, walks into a tech store with a mental list of PC components.
Partway round he spots an **advanced cooling system** that wasn't on his list and adds it.
Later he finds a better graphics card and **swaps** it for the one he'd planned.

His list **changed as he went** — which is exactly what a mutable list does.

---

### **2. Creating an Immutable List — `listOf`**

```kotlin
val shoppingList = listOf("Processor", "RAM", "Graphics card", "SSD")
```

This list is **immutable**: it cannot be changed after creation.

```kotlin
shoppingList.add("Cooling system")     // ❌ no such method
```

There is **no `add`** — the method simply doesn't exist on this type.

> ⚠️ This has **nothing to do with `val`**. The immutability comes from `listOf`, not from
> the keyword. `val` stops you reassigning the *variable*; `listOf` stops you changing the
> *contents*.

---

### **3. Creating a Mutable List — `mutableListOf`**

```kotlin
val shoppingList = mutableListOf("Processor", "RAM", "Graphics card", "SSD")
```

Same syntax, but now `.add()`, `.remove()` and friends exist. Note it's still a **`val`** —
the variable never gets reassigned, only the list's contents change.

#### The two ways to write it

```kotlin
val empty = mutableListOf<String>()              // typed, empty — Day 4's BankAccountApp
val full  = mutableListOf("Processor", "RAM")    // type inferred from the items
```

An **empty** list needs the explicit `<String>`, because there's nothing for Kotlin to infer
from — the same rule you saw in the BankAccountApp lecture.

---

### **4. Adding and Removing**

```kotlin
shoppingList.add("Cooling system")           // append at the end
shoppingList.remove("Graphics card")         // remove by value
```

`remove` also has variants: by **index**, or the **first** / **last** item.

> 💡 **Method vs function:** a function called *on an object* (`list.add(...)`) is
> conventionally called a **method**. In Kotlin the terms are interchangeable; in some
> languages (JavaScript, for instance) they are not.

---

### **5. Order Matters — `add` Appends**

Swapping the graphics card reveals something important:

```kotlin
shoppingList.remove("Graphics card RTX 3060")
shoppingList.add("Graphics card RTX 4090")
```

Printing the list:

```text
[Processor, RAM, SSD, Cooling system, Graphics card RTX 4090]
```

The new card is **at the end**, not in the old slot — because `remove` deleted the middle
item and `add` (without an index) **appends**. Controlling position needs an index, which is
the next lecture.

---

### **6. What a List Can Hold**

Lists are not limited to strings or numbers. They can hold:

* `String`, `Int`, `Double`, any primitive
* **Objects of your own classes** — e.g. `CoffeeDetails`
* Objects of Kotlin's own classes

This is what makes lists powerful: the Day 4 BankAccountApp stores a list of transaction
**strings**, and Day 7's Shopping List app stores a list of **custom objects**.

---

### **7. Which One Should You Use?**

| Need | Use |
| :--- | :--- |
| Fixed data that must never change | **`listOf`** |
| Data you'll add to or remove from | **`mutableListOf`** |

Prefer `listOf` when you can — an immutable list can't be corrupted by accident.

---

### **Key Takeaways**

1. **`listOf(...)`** → immutable; **`mutableListOf(...)`** → mutable.
2. Immutability comes from **`listOf`**, *not* from `val` — they control different things.
3. Only mutable lists have **`.add()`** and **`.remove()`**.
4. An empty mutable list needs an explicit type: **`mutableListOf<String>()`**.
5. **`add` without an index appends to the end** — position control needs an index.
6. Lists hold **any type**, including your own objects.
7. A **method** is just a function called on an object.
