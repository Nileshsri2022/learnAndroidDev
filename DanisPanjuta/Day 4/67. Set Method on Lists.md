Here is a clear, structured breakdown of the short lecture on the **`set` method** — the
explicit alternative to bracket assignment.

---

### **1. Syntax**

```kotlin
shoppingList.set(1, "Water cooling")
```

| Argument | Meaning |
| :--- | :--- |
| **`1`** | The **index** to replace |
| **`"Water cooling"`** | The **new element** |

It replaces whatever is at that index with the new value — identical in effect to
`shoppingList[1] = "Water cooling"`.

---

### **2. The Result**

```text
Before: [Processor, Cooling system, RAM, Graphics card]
After:  [Processor, Water cooling, RAM, Graphics card]
```

Position preserved, length unchanged.

---

### **3. Two Ways to Do the Same Thing**

```kotlin
shoppingList[1] = "Water cooling"          // indexing operator
shoppingList.set(1, "Water cooling")       // explicit method
```

Android Studio shows a hint on the `set` version: **"use the indexing operator"** — Kotlin
prefers the bracket form as more idiomatic.

---

### **4. Which Should You Use?**

Both compile to the same behaviour. The choice is **stylistic**:

| Consider | |
| :--- | :--- |
| **Idiomatic Kotlin** | Bracket notation — what the IDE recommends |
| **Explicitness** | `set(...)` reads more obviously to someone from Java |
| **Team style guide** | **Follow it** — consistency beats personal preference |

The instructor's point: Kotlin's own preference shifts between versions, so don't over-index
on IDE hints. Either is fine; **match your team**.

---

### **5. The General Lesson**

Kotlin frequently offers **more than one correct way** to do something. Recognising that —
and deferring to the local convention — is part of working in a real codebase.

---

### **Key Takeaways**

1. **`set(index, element)`** replaces the item at that index.
2. It is **functionally identical** to `list[index] = element`.
3. The IDE suggests the **bracket form** as more idiomatic Kotlin.
4. Neither is wrong — **follow your team's style guide**.
5. Replacing preserves **position and length**; it is not a remove-and-add.
