# Welcome to Day 10

---

## Overview

Day 10 focuses on a single, essential capability: moving from one screen to another. Very few
apps ship with only one screen. Detail views, login flows, settings, and checkout steps all require
transitions between destinations. In Jetpack Compose that is handled by the Navigation component.

The day is split into two projects:

| Project | Purpose |
| :--- | :--- |
| **NavigationSample** | A fresh two-screen app used to learn `NavHost`, `NavController`, routes, and argument passing in isolation |
| **MyRecipeApp** | Yesterday's recipe app, extended with a `CategoryDetailScreen` reached by tapping a category tile |

---

## What you will build and learn

| Topic | Why it matters |
| :--- | :--- |
| NavController | The central, stateful API that drives navigation and owns the back stack |
| NavHost | The container that maps routes to composable destinations |
| Routes | Stable string identifiers that let any part of the app reach a destination |
| Back stack | Gives the system back button predictable behaviour |
| Passing simple arguments | Send a name typed on one screen to the next screen |
| Passing objects | Send an entire `Category` to a detail screen via `SavedStateHandle` |
| Sealed-class routes | Centralize destination strings so typos fail at compile time |
| Parcelable / `@Parcelize` | Make a data class transportable so it can survive the journey |

## Day 10 roadmap

1. Build `FirstScreen` — a text field for a name plus a "Go to next screen" button.
2. Build `SecondScreen` — a greeting plus a "Go to first screen" button.
3. Add the Navigation dependency and wire up `NavHost` and `NavController`.
4. Pass the entered name from the first screen to the second screen.
5. Create `CategoryDetailScreen` for the recipe app (title, image, scrollable description).
6. Make the category tiles clickable and hoist the navigation callback upwards.
7. Define the routes in a `sealed class Screen`.
8. Implement the recipe app navigation graph and pass a whole object through it.
9. Make `Category` `@Parcelize`d so it can be stored in the `SavedStateHandle`.

---

## Key idea

Navigation is centralized. Screens do not know how to navigate — they simply invoke a callback
handed to them. The graph (inside `NavHost`) owns the destinations, and the `NavController`
performs the actual `navigate()` calls. This keeps composables reusable, preview-friendly, and easy
to test.

---

## Looking ahead

Navigation in Compose is more involved than the old XML/intent approach for simple cases, but it
scales far better once an app has many destinations. The pattern learned today — routes, a graph,
hoisted navigation lambdas, and parcelable arguments — is reused in every later app in the course.

---

## Recap / cheat sheet

- **NavController:** stateful API that tracks the back stack and performs navigation.
- **NavHost:** hosts the navigation graph; needs a controller and a `startDestination`.
- **Route:** a string that identifies a destination from anywhere in the app.
- **Back stack:** the ordered history of screens the back button walks through.
- **Hoisting:** screens receive `(Category) -> Unit` style callbacks instead of navigating themselves.
- **Parcelable:** the serialization contract that lets complex objects travel between destinations.
