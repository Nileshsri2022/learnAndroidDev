## What you can do now

You can change a variable, and the screen follows. You can change the screen (type, tap a menu), and the variable follows. No manual `findViewById`, no extra “refresh UI” call.

That loop is the whole day:

```
Event  →  update State  →  Recomposition  →  new UI
```

---

## Recap — concepts from Day 6

| Concept | In one sentence |
| :--- | :--- |
| **State** | A value that changes over time (`inputValue`, `iExpanded`, …) |
| **Event** | A user (or system) action: click, typing, dismiss |
| **Recomposition** | Compose re-runs the composables that read the changed state |
| **`mutableStateOf`** | Makes a value *observable* so Compose notices changes |
| **`remember`** | Keeps that value alive across recompositions |
| **`by`** | Lets you write `count = 1` instead of `count.value = 1` |
| **Elvis `?:`** | `toDoubleOrNull() ?: 0.0` — default if parse fails |
| **`MaterialTheme.typography`** | Ready-made text styles (`headlineLarge`, …) |

## Recap — the Unit Converter

* `OutlinedTextField` is controlled: `value` + `onValueChange`
* Two dropdowns, two expanded flags, two conversion factors
* Meters are the base unit; other units are “how many meters is 1 of this?”
* `convertUnits()` runs on typing **and** on every unit change
* Button labels show `inputUnit` / `outputUnit`
* Copy-paste between the two menus is how the calculation bug happened
