# TheMealDB and How We Will Use It

---

## Overview

The project uses **TheMealDB**, a recipe service with a JSON API. Instead of inventing and maintaining recipe data, the app requests information that the service already collects, including category names, meal details, ingredients, instructions, and image locations.

---

## API request and response

An **API** (Application Programming Interface) is a defined way for software to interact. A REST-style API exposes endpoints that a client can request over HTTP. The client makes a request; the service sends an HTTP response, often containing JSON.

TheMealDB offers different endpoints for searching by name, looking up meals, listing meals by letter, and requesting a random meal. The category-browser milestone begins with the categories endpoint. The service's documentation is the source of truth for exact URLs, keys, and response fields.

```text
Android app  -- HTTP GET -->  TheMealDB endpoint
Android app  <-- JSON response --  TheMealDB
```

Some API features may have different access or key requirements. Keep credentials out of source control if an endpoint requires a private key; use the provider's documented test/development key only where permitted.

---

## What a meal response can contain

A meal object can include an identifier, name, category, origin/area, instructions, image URL, and ingredient/measure fields. A `meals` property may hold a list of matching meal objects. A URL to an image is text in the response; an image-loading library can request the image separately.

---

## Inspect before modeling

1. Open the provider's endpoint in a browser or API client.
2. Format the JSON so its nesting is visible.
3. Identify which object or array contains the data the screen needs.
4. Record exact JSON property names and value types.
5. Model only the fields required for the current screen.

The app's first screen needs category data, not every meal detail. Start with the smallest response model that supports that screen.

---

## Recap / cheat sheet

- An endpoint identifies the resource/action being requested.
- HTTP `GET` reads data; other methods serve different purposes.
- The service response is structured data, not a ready-made UI.
- An image URL points to a separate remote resource.
- Check the API documentation for usage terms, keys, and response schemas.
