# Try, Catch, and Finally

---

## Overview

Input and network operations can fail. A value that cannot be converted to a number, for example, throws a `NumberFormatException`. A `try`/`catch` block handles an expected failure path so the whole program need not terminate unexpectedly.

---

## Basic shape

```kotlin
try {
    val number = readLine()?.toInt()
    println("User entered $number")
} catch (e: NumberFormatException) {
    println("Please enter a valid number: ${e.message}")
} finally {
    println("This runs whether the conversion succeeded or failed")
}
```

| Block | Purpose |
| :--- | :--- |
| `try` | Runs code that may throw an exception |
| `catch` | Handles a matching exception and provides a recovery/reporting path |
| `finally` | Runs after the try/catch path, commonly for cleanup |

The lecture also shows catching the broader `Exception` type. Prefer catching a specific exception when practical; a broad catch can hide programming errors if used carelessly.

---

## In a network request

A request can fail because the device is offline, the endpoint is incorrect, the server is unavailable, or the response cannot be parsed. Catch failures in the data-loading flow, update the screen's error state, and stop showing the loading indicator.

```kotlin
try {
    val response = apiService.getCategories()
    // Publish successful response to UI state.
} catch (e: Exception) {
    // Publish a useful error message and end loading.
}
```

A robust app should present a clear message and, where appropriate, offer retry. Do not treat every exception as the same issue in a production error-reporting strategy.

---

## Recap / cheat sheet

- Use `try` around operations that may fail.
- Handle failures in `catch`; `e.message` may itself be nullable.
- `finally` is for work that must happen regardless of success/failure.
- Handle network and user-input failures gracefully rather than letting them crash the experience.
