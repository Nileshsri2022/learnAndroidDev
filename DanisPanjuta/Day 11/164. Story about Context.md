# Story about Context

---

## Overview

`Context` appears in almost every Android API signature, and it is rarely explained well. This
lecture uses a short story — the realm of **Aptom** — to give it a shape.

The one-sentence version: **`Context` is the energy that lets a piece of code reach the rest of the
app and the system.** Without it you cannot read resources, start activities, or ask for a location.

---

## The realm of Aptom

Every village is an app, and every inhabitant needs a unique form of energy to carry out their tasks.
That energy is **context**.

| Layer of Aptom | Android equivalent | What it provides |
| :--- | :--- | :--- |
| The earth itself | **Base context** | Fundamental utilities and services — accessing resources, launching activities, and more |
| The village centre | **Activity context** | A variation of that energy tailored to the village's inhabitants; drawn from whenever a task happens inside the village |
| The outposts scattered around | **Service context** | Its own reservoir, so background tasks can run without tapping into the village centre |
| The watchtowers | **Broadcast receiver context** | Catches signals from afar and has its own context to process and relay them |

For the location app the relevant one is the **activity context** — the app has a single screen and
everything happens in it.

---

## Why location needs a context

Two of the three location APIs used in this day take a `Context` as their first argument:

```kotlin
class LocationUtils(val context: Context) {

    // 1. Checking a permission — the system needs to know *which app* is asking
    ContextCompat.checkSelfPermission(context, Manifest.permission.ACCESS_FINE_LOCATION)

    // 2. Creating the location client — bound to this app's environment
    private val fusedLocationClient: FusedLocationProviderClient =
        LocationServices.getFusedLocationProviderClient(context)

    // 3. Building the geocoder — bound to this app's environment and locale
    //    Geocoder(context, Locale.getDefault())
}
```

That is also why `LocationUtils` stores the context as a constructor property: every method in the
class needs it, so it is handed over once.

In Compose the context comes from `LocalContext.current`, which yields the context of the activity
the composable is currently running in.

## Context leakage

> Energy must flow seamlessly. However, if the context from one village seeps into another, it causes
> turmoil.

Developers are the guardians of Aptom: use context wisely and make sure it does not **leak**.

A leak happens when something long-lived (a static field, a singleton, a background thread) keeps a
reference to something short-lived (an activity's context). The activity can no longer be garbage
collected, so its whole view tree stays in memory. Symptoms are a growing memory footprint, a laggy
app, and eventually an `OutOfMemoryError`.

Rules of thumb:

- Do not store an activity context in an object that outlives the activity.
- Prefer the application context for anything long-lived.
- A `ViewModel` should never hold a `Context` directly — use `AndroidViewModel` if it truly needs one.

---

## Recap / cheat sheet

- **Context** is the handle to the app's environment: resources, activities, system services.
- Base context → Activity context → Service context → Broadcast receiver context.
- Location code needs it for `checkSelfPermission`, `getFusedLocationProviderClient`, and `Geocoder`.
- In Compose, get it with `LocalContext.current`.
- Never let a short-lived context be held by something long-lived — that is a **context leak**.
