# Welcome to Day 11

---

## Overview

Day 11 is about **location**: finding out where the device is, in terms of latitude and longitude,
and potentially turning those coordinates into a readable address.

Location is one of those capabilities that feels obvious until you have to build it. It requires a
system service, a permission the user can refuse, a callback that delivers results asynchronously,
and a view model to hold the data.

---

## Why location matters

Almost every real app touches it in some way:

| App type | What location is used for |
| :--- | :--- |
| Delivery services | Knowing where to deliver an item |
| Shopping apps | Pre-filling the shipping address from the current position |
| Ride hailing (Uber and similar) | Matching the rider and the driver at a pickup point |
| Maps and navigation | Routing, distance, points of interest |
| Games (Pokémon Go) | Placing the player precisely in the real world |

Every one of these needs two things from you as a developer: the location APIs, and the **user's
permission** to call them.

---

## What you will learn

| Topic | Why it matters |
| :--- | :--- |
| `ACCESS_COARSE_LOCATION` / `ACCESS_FINE_LOCATION` | The two manifest permissions location is built on |
| Runtime permission checks | The manifest is not enough — the user decides at runtime |
| `ContextCompat.checkSelfPermission` | Asking the system whether permission was granted |
| `Context` | The handle into app resources and services that location APIs require |
| `rememberLauncherForActivityResult` | The Compose way to open the system permission dialog |
| `ActivityResultContracts.RequestMultiplePermissions` | Requesting several permissions in one prompt |
| Permission rationale | Explaining to the user why the feature needs access |
| `FusedLocationProviderClient` | Google Play Services' entry point for reading a position |
| `LocationCallback` | Receiving location updates asynchronously |
| `LocationViewModel` | Holding the position so it survives recomposition |
| `Geocoder` | Converting latitude and longitude into an address |
| Emulator location controls | Faking a position and replaying a route for testing |

## Day 11 roadmap

1. Create the **LocationApp** project and declare the location permissions in `AndroidManifest.xml`.
2. Build `LocationUtils`, a helper class that checks whether permission has been granted.
3. Understand `Context` — what it is and why location code needs it.
4. Build the UI: a `Text` showing the position and a **Get Location** button.
5. Wire up `rememberLauncherForActivityResult` and request both permissions at once.
6. Handle the rationale case and the "go to Settings" case with toasts.
7. Add `LocationViewModel` and the `LocationData` data class.
8. Read latitude and longitude through the fused location provider and display them.
9. Use the emulator's extended controls to set a fake position and replay a route.
10. Reverse-geocode the coordinates into an address with `Geocoder`.

---

## A note on how much is reusable

Location code is **boilerplate-heavy but stable**. The permission launcher, the callback, the
location request builder and the geocoder look almost identical in every project. Learn them once
here, then copy them into whatever app needs them.

## Recap / cheat sheet

- **Location = latitude + longitude**, optionally turned into an address.
- **Two permissions:** coarse (approximate) and fine (precise, GPS).
- **Manifest is not enough** — permission must also be granted at runtime.
- **Context** is the handle that lets code reach Android services.
- **ViewModel** holds the position; the UI observes it.
- **Geocoder** turns coordinates into human-readable text.
