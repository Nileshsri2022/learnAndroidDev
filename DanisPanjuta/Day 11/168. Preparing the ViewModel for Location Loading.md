# Preparing the ViewModel for Location Loading

---

## Overview

Permission is settled; now the app needs somewhere to **put** a location once it arrives. This
lecture adds the `LocationData` model, the `LocationViewModel` that holds it, and the two Gradle
dependencies that make location possible.

---

## Step 1 — the model

```kotlin
data class LocationData(
    val latitude: Double,
    val longitude: Double
)
```

Two `Double`s and nothing else. A data class gives `equals`, `toString` and `copy` for free, which
matters later when the position updates every second.

---

## Step 2 — the view model

```kotlin
class LocationViewModel : ViewModel() {

    private val _location = mutableStateOf<LocationData?>(null)
    val location: State<LocationData?> = _location

    fun updateLocation(newLocation: LocationData) {
        _location.value = newLocation
    }
}
```

Extending `ViewModel()` requires the `androidx.lifecycle.viewmodel` import.

### The backing-property pattern

| Member | Visibility | Type | Role |
| :--- | :--- | :--- | :--- |
| `_location` | `private` | `MutableState<LocationData?>` | Writable — only the view model can change it |
| `location` | public | `State<LocationData?>` | Read-only from the outside |
| `updateLocation(...)` | public | function | The single controlled way in |

The outside world can observe the location but cannot overwrite it. This is Kotlin's equivalent of a
getter/setter pair: `_location` is the field, `updateLocation` is the setter, `location` is the getter.

### Why `null` and not a default position

`null` means *no data yet*. Inventing `LocationData(0.0, 0.0)` instead would be a real coordinate — in
the Gulf of Guinea — and the UI could not distinguish "not loaded" from "loaded, and the user is at
(0,0)". The nullable type makes the not-loaded state impossible to misread.

### The `State` import trap

> This is a tricky one. I really needed to check, because sometimes there are different imports and
> they do different things, and suddenly the code wouldn't work and you wouldn't understand why.

The correct `State` is **`androidx.compose.runtime.State`**. Other `State` types exist
(`androidx.lifecycle.*` among them) and Android Studio will offer them. Importing the wrong one
compiles-looking code that does not behave.

## Step 3 — thread the view model through the UI

`LocationDisplay` is the composable that shows the position, so it needs the view model:

```kotlin
@Composable
fun LocationDisplay(
    locationUtils: LocationUtils,
    viewModel: LocationViewModel,
    context: Context
) { ... }
```

And the parent passes it down, with the responsibility hoisted further up:

```kotlin
@Composable
fun MyApp(viewModel: LocationViewModel) {
    val context = LocalContext.current
    val locationUtils = LocationUtils(context)
    LocationDisplay(locationUtils = locationUtils, viewModel = viewModel, context = context)
}
```

The instance is created in `onCreate`, inside `setContent`:

```kotlin
setContent {
    val viewModel: LocationViewModel = viewModel()
    LocationAppTheme {
        Surface(...) {
            MyApp(viewModel)
        }
    }
}
```

`viewModel()` scopes the instance to the activity, so it survives rotation — the point of Day 8.

## Step 4 — the dependencies

Android Studio offers "add dependency and import" as a single quick-fix. Two are needed beyond the
view model one:

```kotlin
dependencies {
    // Created automatically by the quick-fix on `viewModel()`
    implementation("androidx.lifecycle:lifecycle-viewmodel-compose:<version>")

    // Added manually — the location API itself
    implementation("com.google.android.gms:play-services-location:21.0.1")

    // Added later, for LatLng in the geocoding lecture
    implementation("com.google.android.gms:play-services-maps:<version>")
}
```

| Dependency | What it unlocks |
| :--- | :--- |
| `lifecycle-viewmodel-compose` | The `viewModel()` function in composables |
| `play-services-location:21.0.1` | `FusedLocationProviderClient`, `LocationCallback`, `LocationRequest`, `Priority` |
| `play-services-maps` | `LatLng`, and the maps features used from Day 12 onward |

`play-services-location` gives access to Google Play location services — which is also what makes it
possible to translate latitude and longitude into an address later on. Sync Gradle after each addition.

---

## Recap / cheat sheet

- `data class LocationData(val latitude: Double, val longitude: Double)` — the model.
- Private `mutableStateOf<LocationData?>(null)`, public `State<LocationData?>`, one `updateLocation`.
- `null` = no data yet; never fake a default position.
- Import **`androidx.compose.runtime.State`**.
- Create the view model with `viewModel()` inside `setContent`, pass it down.
- Dependencies: `lifecycle-viewmodel-compose`, `play-services-location:21.0.1`, `play-services-maps`.
