# Requesting for Permission and Seeing the Popup

---

## Overview

The launcher exists but does nothing yet. This lecture fills in the `else` branch — what happens when
the user refuses — launches the request from the button, adds a parent composable to supply the
context, and finally sees the system dialog.

> The pattern built here is not specific to location. It is the pattern for **any** runtime
> permission the app will ever need to request.

---

## Step 1 — do we need to explain ourselves?

Android distinguishes "the user said no once" from "the user cannot be asked again". The signal is the
**rationale**:

```kotlin
val rationaleRequired = ActivityCompat.shouldShowRequestPermissionRationale(
    context as MainActivity, Manifest.permission.ACCESS_FINE_LOCATION
) || ActivityCompat.shouldShowRequestPermissionRationale(
    context as MainActivity, Manifest.permission.ACCESS_COARSE_LOCATION
)
```

It takes an activity and a permission (non-null) and returns a Boolean: should the app explain *why*
it wants this permission before asking again?

`context as MainActivity` pins the rationale to this activity's window — "do not show this from some
other screen". The cast is not strictly required, since the plain `context` would behave the same
here, but it makes the intent explicit.

---

## Step 2 — the two toasts

```kotlin
if (rationaleRequired) {
    Toast.makeText(
        context,
        "Location Permission is required for this feature to work",
        Toast.LENGTH_LONG
    ).show()
} else {
    Toast.makeText(
        context,
        "Location Permission is required. Please enable it in the Android Settings",
        Toast.LENGTH_LONG
    ).show()
}
```

| Branch | Situation | Message |
| :--- | :--- | :--- |
| `rationaleRequired == true` | The user can still be asked in-app | Explain what breaks without the permission |
| `rationaleRequired == false` | The permission was denied permanently | Tell the user to change it in Android Settings |

A toast is the little text indicator at the bottom of the screen. `makeText` takes the context, the
text and the duration; `.show()` is what actually displays it. Nothing appears until `.show()` is
called.

A toast is the simplest possible rationale. A real app might use a dialog or an inline banner — the
structure stays the same.

---

## Step 3 — launch from the button

```kotlin
Button(onClick = {
    if (locationUtils.hasLocationPermission(context)) {
        // already granted — go straight to reading the position
    } else {
        requestPermissionLauncher.launch(
            arrayOf(
                Manifest.permission.ACCESS_FINE_LOCATION,
                Manifest.permission.ACCESS_COARSE_LOCATION
            )
        )
    }
}) {
    Text(text = "Get Location")
}
```

`launch` takes an **array** of permissions. Two are requested here; seven would work exactly the same
way. The order does not matter.

The boilerplate around it never changes — only the array contents do.

---

## Step 4 — a parent composable

`LocationDisplay` needs a context and a `LocationUtils`, so a parent supplies them:

```kotlin
@Composable
fun MyApp() {
    val context = LocalContext.current          // the context of the current activity
    val locationUtils = LocationUtils(context)

    LocationDisplay(locationUtils = locationUtils, context = context)
}
```

`LocalContext.current` "provides a context that can be used by Android applications" — in practice,
the activity the composable is running inside.

---

## Step 5 — call it from `onCreate`

```kotlin
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            LocationAppTheme {
                Surface(
                    modifier = Modifier.fillMaxSize(),
                    color = MaterialTheme.colorScheme.background
                ) {
                    MyApp()
                }
            }
        }
    }
}
```

---

## Step 6 — run it

The app shows **"Location not available"** and a **Get Location** button. Tapping the button brings up
the system dialog:

```text
Allow LocationApp to access this device's location?

  [Precise]  ← toggle, corresponds to ACCESS_FINE_LOCATION

  While using the app     Only this time     Don't allow
```

Two permissions were requested at once, which is why a single dialog covers both: **Approximate**
(coarse) and the **Precise** toggle (fine).

Choosing *While using the app* grants access — although nothing is displayed yet, because reading the
position is the next lecture's job.

---

## A manifest gotcha from the run

An auto-generated permission that the app did not need was present in the manifest and caused a small
problem at launch. Deleting it fixed the app. Check the manifest when something behaves oddly after
using an Android Studio quick-fix.

---

## Recap / cheat sheet

- `ActivityCompat.shouldShowRequestPermissionRationale(activity, permission)` → is an explanation due?
- Rationale required → explain the feature. Not required → point the user to Android Settings.
- `requestPermissionLauncher.launch(arrayOf(...))` opens the system dialog.
- One launcher handles many permissions; only the array changes between apps.
- `LocalContext.current` supplies the activity context to composables.
- Always chain `.show()` onto `Toast.makeText(...)`.
