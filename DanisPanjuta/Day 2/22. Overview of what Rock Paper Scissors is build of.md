Here is a clear, structured breakdown of the lecture that **plans the Rock, Paper, Scissors
game before writing any code** — working out what information the program needs.

---

### **1. Overview**

Before touching the keyboard, the instructor asks a design question: *what does this game
actually need to know?* Answering it reveals exactly which language features are required.

---

### **2. The Information Flow**

```
        ┌─────────────────┐          ┌──────────────────────┐
        │  PLAYER'S CHOICE │          │  COMPUTER'S CHOICE   │
        │  (user input)    │          │  (random)            │
        └────────┬────────┘          └──────────┬───────────┘
                 │                              │
                 │      ┌───────────────┐       │
                 └──────►   COMPARE     ◄───────┘
                        │  who won?     │
                        └───────┬───────┘
                                │
                        ┌───────▼───────┐
                        │ DISPLAY RESULT │
                        └───────────────┘
```

Three pieces of state must exist **at the same time**:

1. What the **player** chose
2. What the **computer** chose
3. The **result** of comparing them

---

### **3. Mapping Requirements to Kotlin Features**

| Requirement | Kotlin feature you need to learn |
| :--- | :--- |
| Store the player's choice | **Variables** |
| Store the computer's choice | **Variables** |
| Distinguish a number from text | **Data types** |
| Answer "did the player win?" | **`Boolean`** — true/false |
| Branch on the comparison | **Conditions** (`if`) |
| Read what the user typed | **User input** (`readln()`) |
| Show the outcome | **Output** (`println()`) |

---

### **4. Why `Boolean` Matters Here**

A condition like *"player chose scissors AND computer chose rock"* is not a number or a
string — it is **true or false**. That is what the `Boolean` type stores, and it is the
foundation of every condition you will ever write.

---

### **5. The Key Insight About Variables**

The lecture ends with the definition that the next video expands on:

> A **variable** stores data **for the lifetime of the program**.

It is **not permanent storage**. Close the app and the data is gone. (Permanent storage —
databases — comes much later, with Room on Day 14.)

---

### **Key Takeaways**

1. **Design before code.** Listing what the program must know tells you which language
   features you need.
2. The game needs **three pieces of state**: player choice, computer choice, result.
3. **Variables** hold data, **data types** say what kind of data, **booleans** drive
   conditions.
4. Variables are **temporary** — they live only while the app runs.
5. The flow is simple on purpose: the complexity is in learning the concepts, not the game.
