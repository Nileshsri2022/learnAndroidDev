Here is a clear, structured breakdown of the lecture on **`while` loops driven by user
input** — and the exercise that finally closes the loop opened in *Rock Paper Scissors
Part 3*.

---

### **1. Overview**

The previous lecture looped on a **counter**. This one loops on a **condition that the user
controls** — the pattern you need for input validation.

---

### **2. The Naive Attempt — And Why It Hangs**

```kotlin
var userInput = readln()

while (userInput == "1") {
    println("While loop is executed")
}
```

Enter `1` and the loop runs **forever**.

#### Why

`userInput` is read **once, before the loop**. Nothing inside the loop changes it, so
`userInput == "1"` stays `true` on every iteration. The condition can never become false.

> ⚠️ Also note **`==`** (compare), not `=` (assign). Mixing these up here silently breaks
> the loop.

---

### **3. Fix #1 — `break`**

```kotlin
while (userInput == "1") {
    println("While loop is executed")
    break                      // leave immediately
}
println("Loop is done")
```

This runs **once** and exits. It works, but as the instructor points out, if you only ever
want one execution you didn't need a `while` at all.

---

### **4. Fix #2 — Re-read the Input Inside the Loop ✅**

```kotlin
var userInput = readln()

while (userInput == "1") {
    println("While loop is executed")
    userInput = readln()       // ← ask again, so the condition can change
}
println("Loop is done")
```

Session:

```text
1
While loop is executed
1
While loop is executed
n
Loop is done
```

Now the condition is **re-evaluated against fresh data** each iteration. Typing anything
other than `1` ends the loop and execution continues after it.

---

### **5. The Pattern**

```
read input
   ↓
┌─► is the input still "keep going"? ── no ──► exit, continue after the loop
│            │ yes
│            ▼
│      do the work
│            ▼
└──── read input again
```

The **re-read at the bottom is what makes it terminate.** Omit it and you have an infinite
loop.

---

### **6. 🎯 The Exercise — Finishing Rock, Paper, Scissors**

This is the payoff. The instructor assigns:

> *"Go back to our Rock, Paper, Scissors application and check whether the player entered
> **rock**, **paper** or **scissors**. If they entered none of those three, prompt them again
> — and keep doing so until they finally enter a valid choice."*

#### Why it matters

Recall the bug from *Rock Paper Scissors Part 3*: invalid input like `"rock source"` fell
through every winning check into the final `else`, so **the computer won automatically**. The
player lost without having played.

#### Sketch of the solution

```kotlin
var playerChoice = readln()

while (playerChoice != "rock" && playerChoice != "paper" && playerChoice != "scissors") {
    println("Invalid choice — please enter rock, paper or scissors:")
    playerChoice = readln()
}
```

The condition combines three comparisons with **`&&`**: the loop continues only while *all
three* "not equal" checks hold, i.e. while the input matches none of the valid options.

---

### **Key Takeaways**

1. Loops driven by user input must **re-read the input inside the loop**, or they never
   terminate.
2. Reading input **once before** the loop is the classic infinite-loop mistake.
3. **`break`** exits immediately — useful, but often a sign you didn't need a loop.
4. Use **`==`** to compare; `=` assigns.
5. **This is the fix Rock, Paper, Scissors has been missing**: a validation loop stops
   invalid input from silently awarding the win to the computer.
6. The pattern generalises to **every** input-validation problem you'll meet in Android.
