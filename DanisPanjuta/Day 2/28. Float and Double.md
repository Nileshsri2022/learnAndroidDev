Here is a clear, structured breakdown of the lecture on **floating-point numbers** — `Float`
and `Double` — the types used whenever a number has a decimal point.

---

### **1. The Two Floating-Point Types**

| Type | Size | Precision | Default? |
| :--- | :--- | :--- | :--- |
| **`Float`** | 32 bit | ~7 significant digits | No |
| **`Double`** | 64 bit | ~15–16 significant digits | ✅ **Yes** |

**Kotlin uses `Double` by default.** Memory is cheap, so there is little reason to reach for
the smaller type.

---

### **2. Inference**

```kotlin
val pi = 3.14
println(pi)        // 3.14
```

Hovering `pi` shows **`Double`** — any decimal literal is a `Double` unless you say
otherwise.

---

### **3. Forcing a `Float`**

Add an **`f`** suffix to the literal:

```kotlin
val pi = 3.14f       // now a Float
```

The annotation form also works, **but you still need the `f`**:

```kotlin
val pi: Float = 3.14     // ❌ type mismatch — 3.14 is a Double
val pi: Float = 3.14f    // ✅
```

---

### **4. The Precision Problem**

The instructor stores π to ten decimal places in a `Float`:

```kotlin
var pi = 3.1415926535f
```

Android Studio underlines it:

> *"The floating-point literal cannot be represented with the required precision."*

And the printed value comes back **rounded**, not merely truncated — the trailing digits
become something like `…2653**7**`. That is the danger: a `Float` doesn't just lose digits,
it **silently changes the value**.

Remove the `f` from both assignments and the full precision returns:

```kotlin
var pi: Double = 3.1415926535   // ✅ exact
```

---

### **5. `val` vs `var` Revisited**

π itself never changes, so `val` feels right — but the *amount of precision you store* does
change during the demo, which requires reassignment and therefore `var`. The lecture quietly
reinforces the rule from earlier: **you cannot reassign a `val`.**

---

### **6. Why This Matters Later**

You already saw the same class of problem in the Day 4 BankAccountApp, where a `Double`
balance printed as `2510.0000000000005`. Floating-point types **cannot represent all decimal
fractions exactly** — which is why financial code uses `BigDecimal` or whole-number cents.

---

### **Key Takeaways**

1. Two decimal types: **`Float`** (32-bit) and **`Double`** (64-bit).
2. **`Double` is the default** for any decimal literal.
3. Force a `Float` with an **`f` suffix** — required even when you annotate the type.
4. A `Float` that can't hold your digits **rounds them**, silently altering the value. The
   IDE warns you; read those warnings.
5. **Prefer `Double`.** Reach for `Float` only when memory genuinely matters.
6. Neither type is exact for money — that's a `BigDecimal` job.
