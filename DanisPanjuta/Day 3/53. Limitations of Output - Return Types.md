Here is a clear, structured breakdown of the short lecture explaining **why the coffee example
has hit a wall** — the motivation for classes.

---

### **1. The Problem**

`askCoffeeDetails()` currently does two jobs at once: it **asks** for the details and then
immediately **makes** the coffee. The instructor wants to separate them:

```
ask for details  →  hand the details to makeCoffee()  →  coffee
```

That requires `askCoffeeDetails()` to **return** the details.

---

### **2. Why That's Not Possible Yet**

A function's return type is **exactly one type**:

| You could return… | But… |
| :--- | :--- |
| an `Int` | only the sugar count — the name is lost |
| a `String` | only the name — the sugar count is lost |
| an array or list of mixed items | possible, but clumsy and unsafe |

The coffee needs **a name AND a sugar count** (and later a size and cream amount). No single
primitive type can carry all of them.

---

### **3. The Answer: Return an Object**

```kotlin
fun askCoffeeDetails(): CoffeeDetails { ... }
```

An **object** can bundle several values of different types into one thing you can pass around
and return.

---

### **4. The Prerequisite: A Class**

Before an object can exist, something must define **what shape it has**:

> To create an object called `CoffeeDetails`, you need a **class** that defines how such
> coffee details have to look.

That means answering: *what information does a coffee need in order to be made?*

### **Key Takeaways**

1. A function returns **exactly one type** — that's the limitation.
2. Real data is usually **several values together** (name + sugar count + size + cream).
3. The solution is to return an **object** that bundles them.
4. An object requires a **class** — the definition of its shape.
5. This is the pivot point of Day 3: everything from here is **object-oriented
   programming**.
