Here is a clear, structured breakdown of the lecture on **return types with `Double`** — and
the integer-division trap that comes with them.

---

### **1. The Setup**

Build a `divide` function. Since dividing two whole numbers can produce a fraction
(3 ÷ 2 = 1.5), it should return a **`Double`**, not an `Int`.

```kotlin
fun divide(num1: Int, num2: Int): Double {
    val result = num1 / num2
    return result
}
```

---

### **2. The Integer Division Trap**

Before fixing it, the instructor demonstrates the problem by returning an `Int`:

| Input | Expected | Actual |
| :--- | :--- | :--- |
| 3 ÷ 2 | 1.5 | **1** |
| 5 ÷ 3 | 1.666… | **1** |

**Integers don't round — they truncate.** Everything past the decimal point is simply
discarded. Even `25.999999…` becomes `25`.

> This is a **silent** wrong answer: no error, no warning, just a result that is quietly
> incorrect. It's one of the most common sources of real bugs.

---

### **3. Why Just Changing the Return Type Isn't Enough**

Declaring `: Double` alone produces an **error**:

```kotlin
val result = num1 / num2      // ❌ Int / Int → Int, but we promised a Double
```

`result` is **inferred** as `Int`, because that's what `Int / Int` yields. Kotlin won't
silently widen it for you.

---

### **4. The Fix: Make One Operand a `Double`**

```kotlin
val result = num1.toDouble() / num2
```

Converting **just one** side is enough. Kotlin's rule:

> If **any** operand in a calculation is a `Double`, the whole result is a `Double`.

Now `5 / 3` returns `1.6666666666666667`.

---

### **5. Better: Accept `Double`s From the Start**

Rather than converting internally, take doubles as parameters and parse the input that way:

```kotlin
fun divide(num1: Double, num2: Double): Double {
    val result = num1 / num2
    return result
}

fun main() {
    println("Enter the first number")
    val num1D = readln().toDouble()

    println("Enter the second number")
    val num2D = readln().toDouble()

    println("The result is ${divide(num1D, num2D)}")
}
```

* **`.toDouble()`** replaces `.toInt()` for parsing.
* Whole numbers still work — typing `5` and `3` gives `1.666…`.
* Decimals work too — `1.5` ÷ `3.5` gives `0.4285…`.
* Typing `asdf` still throws a **`NumberFormatException`** — parsing has the same weakness
  regardless of target type.

---

### **6. Clean Up Your Names**

Changing the types left the old names behind (`num1Str` → `num1D`). The instructor renames
them to match:

> *"That's something we have to consider when working around and playing around with names —
> that we always clean up after us."*

A variable called `num1Int` holding a `Double` will mislead you later.

---

### **7. Precision Limits**

A `Double` holds about **15–16 significant digits**. Beyond that it rounds — which is the
same class of limitation you saw with `Float` on Day 2, and the reason financial code avoids
floating-point types entirely.

---

### **8. What's Coming**

A function can return **one value of one type**. To return a *combination* — a name **and** a
sugar count — you need an **object**. That's the next lectures.

---

### **Key Takeaways**

1. **`Int / Int` truncates** — `5 / 3` is `1`, not `1.666…`, with no warning.
2. To get a fractional result, **at least one operand must be a `Double`**.
3. Changing only the **return type** isn't enough — the inferred expression type must match.
4. Use **`.toDouble()`** to parse decimal input; whole numbers still parse fine.
5. **Rename variables when their type changes** — stale names cause stale bugs.
6. A `Double` carries ~**15–16 digits** of precision.
7. A function returns **one type** — combining values requires an **object**.
