Here is a clear, structured breakdown of the **quiz solution** for adding a second parameter —
naming whose coffee it is.

---

### **1. The Challenge**

The output says how much sugar a coffee has but never **who it's for**. Fix it by adding
another parameter.

---

### **2. Multiple Parameters**

Separate parameters with a **comma**, and give each its own type:

```kotlin
fun makeCoffee(sugarCount: Int, name: String) {
    // ...
}
```

Whitespace around the comma is cosmetic — `sugarCount: Int,name: String` compiles identically.

> **Key point:** parameters do **not** have to share a type. Here one is `Int` and the other
> is `String`. Later you'll pass objects and lists too.

---

### **3. Updating Every Call Site**

Adding the parameter breaks all existing calls, so each now needs a name:

```kotlin
fun main() {
    makeCoffee(1, "Amy")       // one sugar
    makeCoffee(2, "Jimmy")     // two sugars
    makeCoffee(0, "Dennis")    // no sugar
    makeCoffee(30, "Candice")  // mostly sugar
}
```

**Argument order must match the parameter order.** `makeCoffee("Amy", 1)` is a compile-time
error, because `"Amy"` is not an `Int`.

---

### **4. Using Both Parameters**

```kotlin
fun makeCoffee(sugarCount: Int, name: String) {
    if (sugarCount == 1) {
        println("Coffee with one spoon of sugar for $name")
    } else {
        println("Coffee with $sugarCount spoons of sugar for $name")
    }
}
```

Output:

```text
Coffee with one spoon of sugar for Amy
Coffee with 2 spoons of sugar for Jimmy
Coffee with 0 spoons of sugar for Dennis
Coffee with 30 spoons of sugar for Candice
```

---

### **5. Handling Zero**

`"0 spoons of sugar for Dennis"` is grammatical but clumsy. Add a third branch:

```kotlin
fun makeCoffee(sugarCount: Int, name: String) {
    if (sugarCount == 1) {
        println("Coffee with one spoon of sugar for $name")
    } else if (sugarCount == 0) {
        println("Coffee with no sugar for $name")
    } else {
        println("Coffee with $sugarCount spoons of sugar for $name")
    }
}
```

```text
Coffee with no sugar for Dennis
```

> The IDE suggests converting this chain into a **`when`** statement. The instructor admits he
> simply isn't in the habit of using `when` — a useful reminder that IDE suggestions are
> recommendations, not requirements. (You already saw `when` used properly in Day 2's Rock,
> Paper, Scissors.)

---

### **6. What This Unlocks**

The function is now **genuinely reusable**: one definition serves any person with any sugar
count. That's the difference between a hard-coded script and real code.

---

### **Key Takeaways**

1. **Multiple parameters** are comma-separated, each with its **own type**.
2. Parameters can be **mixed types** — `Int` and `String` side by side is normal.
3. **Argument order must match** parameter order, or the compiler rejects it.
4. Adding a parameter breaks all call sites — the IDE lists every one.
5. Chain `if` / `else if` / `else` to handle special cases (`1`, `0`) cleanly.
6. IDE hints like *"use `when`"* are **suggestions**; both forms are valid.
