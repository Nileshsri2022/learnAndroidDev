Here is a clear, structured breakdown of the **bonus quiz solution** — driving the coffee
function from **user input** instead of hard-coded arguments.

---

### **1. The Challenge**

Instead of writing `makeCoffee(1, "Amy")` in the source, **ask the user** for both values at
runtime.

---

### **2. The Solution**

```kotlin
fun main() {
    println("Who is this coffee for?")
    val name = readln()

    println("How many pieces of sugar do you want?")
    val sugarCount = readln().toInt()

    makeCoffee(sugarCount, name)
}
```

Session:

```text
Who is this coffee for?
Dennis
How many pieces of sugar do you want?
0
Coffee with no sugar for Dennis
```

---

### **3. The Details That Matter**

#### Prompt before every read

The first attempt had no prompt for the name — the program just **froze on a blank cursor**.
Always tell the user what to type *before* calling `readln()`.

#### `readln()` returns a `String`

`name` needs no conversion — `makeCoffee` wants a `String`. But `sugarCount` must be an `Int`
because the function compares it numerically:

```kotlin
val sugarCount = readln().toInt()
```

#### Two steps, if that reads better

The instructor first writes it longhand, then collapses it:

```kotlin
val sugarCountString = readln()
val sugarCount = sugarCountString.toInt()
```

Identical behaviour. Since neither is reassigned, both are **`val`** — and the IDE complains
until you change `var` to `val`.

#### Argument order still applies

`makeCoffee(sugarCount, name)` matches `makeCoffee(sugarCount: Int, name: String)`. Swapping
them is a compile-time error.

---

### **4. The Remaining Limitation**

This machine makes **exactly one coffee per run**. Someone ordering for themselves *and* a
colleague has to wait for the first to finish, then run the program again.

The fix is a **loop** — keep asking until the user says they're done. You already have every
piece needed for it: `while`, boolean conditions and `readln()` from Day 2. That's what the
next lecture builds.

---

### **5. Why This Pattern Matters**

This is the shape of **every interactive program**:

```
prompt → read → parse → act
```

Later in the course the "console" becomes an Android text field and the "act" updates a
Compose UI — but the sequence is identical.

---

### **Key Takeaways**

1. Replace hard-coded arguments with **`readln()`** to make a function interactive.
2. **Prompt before each read**, or the user faces a frozen, blank console.
3. **`readln()` returns a `String`** — call `.toInt()` for anything numeric.
4. Use **`val`** for input you never reassign; the IDE will tell you when you got it wrong.
5. **Argument order must match** the parameter list.
6. One run = one coffee. Making it repeat needs a **loop** — the next lecture.
